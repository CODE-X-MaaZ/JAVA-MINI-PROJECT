# Database Schema — Food Rescue Connect

## 1. Purpose

MySQL stores food listings and claims so the application retains data after a page refresh or backend restart.

The schema below is a logical proposal. If entities already exist, compare them to this design and adapt without deleting existing data.

## 2. `food_items` table

| Column | Suggested type | Rules |
|---|---|---|
| `id` | BIGINT | Primary key, auto-generated |
| `food_name` | VARCHAR(120) | Not null |
| `description` | TEXT | Not null |
| `quantity` | DECIMAL(10,2) | Greater than zero |
| `unit` | VARCHAR(30) | Not null |
| `pickup_location` | VARCHAR(255) | Not null |
| `pickup_deadline` | DATETIME | Not null |
| `donor_name` | VARCHAR(120) | Not null |
| `donor_type` | VARCHAR(30) | Not null |
| `status` | VARCHAR(20) | Not null; defaults to `AVAILABLE` |
| `created_at` | DATETIME | Not null |

## 3. `claims` table

| Column | Suggested type | Rules |
|---|---|---|
| `id` | BIGINT | Primary key, auto-generated |
| `food_item_id` | BIGINT | Foreign key to `food_items.id` |
| `recipient_name` | VARCHAR(120) | Required for demo mode |
| `status` | VARCHAR(20) | For example, `CLAIMED` |
| `claimed_at` | DATETIME | Not null |

For the one-claim-per-food MVP, enforce one successful claim per food item with a database constraint where compatible with the chosen model, and use a transaction/locking or atomic-update strategy. A uniqueness constraint is a useful additional safeguard, not a replacement for correct transaction handling.

If future requirements permit re-listing or claim history, design the uniqueness rule around active claims rather than blindly allowing or forbidding all historical claims.

## 4. Relationship

```text
food_items (1) -------- (0..1) claims
             food_item_id
```

This represents at most one successful claim per food listing in the MVP.

## 5. Data integrity

- IDs are generated by the database.
- Quantity must be greater than zero.
- Food status must be one of the supported values.
- A claim must reference an existing food item.
- Only an available listing can be claimed.
- A claim and status update should commit or roll back together.
- Do not store passwords in this schema unless real authentication is explicitly added and implemented safely.

## 6. Local database setup

Create a local database, for example:

```sql
CREATE DATABASE food_rescue_connect;
```

Use a dedicated local development database user where practical. Configure credentials outside version control.

Do not put real passwords into this file or commit them in `application.properties`.
